# План доработки SimpleWMS до рабочего состояния

Дата составления: 09.10.2026

## Цель и границы

Цель — рабочая WMS, которая проходит полный цикл склада и разворачивается одной командой.

**Входит в объём:**

- полный складской цикл: приёмка → размещение → перемещение → заказ → комплектация → отгрузка;
- учёт остатков по партиям и ячейкам, просмотр состояния склада;
- REST API для обмена с ERP. Сама ERP имитируется тестовыми запросами;
- вход по пользователям из БД, роли и права доступа;
- запуск через Docker Compose (приложение + PostgreSQL).

**Не входит** (можно добавить позже): инвентаризация (CycleCount), расширенные отчёты и дашборды, мобильный интерфейс для ТСД, обмен с реальной 1С.

**Технические решения:**

- Схема БД создаётся Hibernate (`ddl-auto=update`).
- Ручные SQL-скрипты (справочные данные, индексы, исправления данных) кладём в `SQL/migrations/`.
- Docker Compose используется как среда «прод».

## Сквозной сценарий приёмки (критерий готовности всего проекта)

1. ERP присылает товары и приходную накладную через API.
2. Кладовщик принимает товар, по каждой строке создаётся партия, остаток появляется в зоне приёмки.
3. Система строит маршрут размещения. Кладовщик подтверждает его, товар переходит в ячейки хранения.
4. ERP присылает заказ клиента. Система резервирует остаток, отдавая первыми партии с ближайшим сроком годности (FEFO).
5. Система строит маршрут комплектации. Комплектовщик собирает заказ, товар переходит в зону отгрузки.
6. Отгрузка проводится, остаток списывается, печатается накладная. ERP получает результат через API.
7. На каждом шаге остатки в `stocks` сходятся с журналом `stock_movements`.

## Этапы

### Этап 0. Фундамент
- Рабочая git-ветка `develop`. Каждый этап — своя ветка от неё.
- `docker-compose.yml` пока только с PostgreSQL, чтобы разработка шла на одинаковой БД.
- Профили настроек: `application-dev.properties` и `application-prod.properties`. Пароли передаются через переменные окружения.
- Скрипт начальных данных `SQL/migrations/V001__seed_reference_data.sql`:
  - системные зоны и ячейки (приёмка, отгрузка);
  - роли и администратор;
  - демо-товары.
- Проверка: проект собирается, `./gradlew bootRun` стартует на чистой БД.

**Готово, когда:** с нуля поднимаются БД и приложение, и открываются все существующие страницы.

### Этап 1. Стабилизация ядра
- Перенести логику из конструкторов (`StockMovement`, `GenerationProductPlacementRoutes`, `UpdateStringReceiving`) в сервисы:
  - `InventoryService` для движений и остатков;
  - `ReceivingProcessService` для приёмки;
  - `PlacementService` для размещения.
- Добавить `@Transactional` на операции, которые меняют несколько таблиц.
- Заменить магические числа на `enum`:
  - `ReceivingStatus`;
  - `MovementType`;
  - статусы маршрутов, заказов и отгрузок.
- Исправить известные ошибки:
  - id новой накладной брать из `save()`, а не через MAX(id);
  - в строке маршрута размещения передавать `qnt`, а не `product_id`;
  - убрать захардкоженную ячейку `location 1`: системные ячейки берутся из справочника или настроек.
- Заменить `System.out` на SLF4J.
- Глобальная обработка ошибок через `@ControllerAdvice`: страница ошибки для UI, JSON для API.
- Первые unit-тесты на движение остатков.

**Готово, когда:** приёмка строки атомарна, тесты на движения проходят.

### Этап 2. Безопасность и пользователи
- Вход по таблице `users` через `UserDetailsService` на базе БД, пароли хранятся в BCrypt.
- Роли: `ADMIN`, `MANAGER` (менеджер склада), `STOREKEEPER` (кладовщик/комплектовщик).
- Права на разделы: справочники и пользователи — ADMIN; документы — MANAGER; исполнение маршрутов — STOREKEEPER.
- Включить CSRF для UI. Для `/api/**` сделать отдельную цепочку с авторизацией по API-ключу.
- Текущий пользователь автоматически подставляется как исполнитель операций (`employeeId`).

**Готово, когда:** без входа ничего не доступно, у каждой роли видны только её разделы.

### Этап 3. Приёмка (доводка)
- Отмена накладной (статус «Отменена»). Запрет правок после завершения.
- Завершение приёмки возможно, только когда все строки обработаны. Расхождения «по документу / факт» видны в итогах.
- В `/api/new_receiving`:
  - проверка входных данных;
  - поиск поставщика по коду, вместо зашитого `1`;
  - понятная ошибка, если товар не найден (сейчас строка молча пропускается).
- Срок годности обязателен для товаров с `expirationDateRequired`.
- ТОРГ-12 по фактическим данным.

### Этап 4. Размещение
- Алгоритм подбора ячейки:
  - зона товара;
  - свободная вместимость по объёму и весу;
  - для класса A — ближние ячейки;
  - одинаковая партия — в одну ячейку.
- Статусы маршрута: создан → в работе → завершён.
- Экран исполнения: кладовщик подтверждает каждую строку, при подтверждении проводится движение «Размещение» из приёмки в ячейку.
- Возможность разместить в другую ячейку с фиксацией фактической.
- Ячейка помечается занятой или свободной (`available`).

### Этап 5. Перемещения
- Документ перемещения: партия, из ячейки, в ячейку, количество.
- Проверка доступного остатка, движение типа «Перемещение».
- В `MovementType` это значение добавляется сверх текущего списка, остальные сохраняются.
- Экран «Остатки в ячейке» и «Где лежит товар».

### Этап 6. Заказы клиентов
- Новые сущности: `customer_order` и `customer_order_line`.
- Статусы: новый → зарезервирован → в сборке → собран → отгружен / отменён.
- Создание вручную и через `POST /api/new_order`.
- Резервирование остатков по FEFO:
  - таблица резервов или поле `reserved` в `stocks`;
  - доступно = остаток − резерв;
  - частичный резерв при нехватке.
- Отмена заказа снимает резерв.

### Этап 7. Комплектация
- Генерация маршрутов сборки по зарезервированным позициям:
  - разбивка по зонам;
  - сортировка по обходу склада (ряд, x, y, z).
- Лист сборки на печать (шаблон `piccking_list.html` уже есть, нужно подключить реальные данные).
- Экран исполнения: подтверждение строк, недостача фиксируется.
- Движение «Сборка» из ячейки в зону отгрузки.

### Этап 8. Отгрузка
- Документ отгрузки по собранным заказам.
- Проведение: движение «Отгрузка» (`toLocation = NULL`), списание остатка и резерва.
- Печатная накладная и статус заказа «Отгружен».
- `GET /api/shipments`: выгрузка результатов для ERP.

### Этап 9. Остатки и базовые отчёты
- «Состояние склада»: остатки по товарам, партиям и ячейкам с фильтрами. Сроки годности подсвечиваются.
- Журнал движений с фильтрами по товару, партии, типу и периоду.
- Главная страница: количество открытых приходов, заказов и маршрутов.
- Пункты меню без реализации («Настройка системы», лишние отчёты, вики) скрыть или сделать заглушки «в разработке».

### Этап 10. API для ERP
- Набор эндпоинтов:
  - справочники: товары, поставщики, клиенты (создание и обновление по коду);
  - приход;
  - заказ;
  - статусы документов;
  - выгрузка результатов приёмки и отгрузки.
- Единый формат ответа и ошибок, валидация через `@Valid`.
- Описание API: OpenAPI/Swagger (springdoc).
- Имитация ERP: коллекция запросов (`.http` или Postman) в `Project_Docs/api/` и тестовые JSON.

### Этап 11. Тестирование
- Unit-тесты сервисов: приёмка, размещение, резерв, сборка, отгрузка.
- Интеграционные тесты на PostgreSQL (Testcontainers).
- Автотест сквозного сценария через API и сервисы.
- Чек-лист ручного тестирования UI в `Project_Docs/`.

### Этап 12. Развёртывание (Docker Compose)
- `Dockerfile`, многоступенчатая сборка: Gradle → JRE 17.
- `docker-compose.yml`:
  - приложение и PostgreSQL;
  - volume для данных;
  - healthcheck;
  - `.env` с настройками.
- Автозагрузка начальных данных при первом запуске.
- Инструкция «Развёртывание» и резервное копирование БД (`pg_dump`).

### Этап 13. Документация (`Project_Docs/`)
Документация пишется по ходу этапов, не в конце. Состав:
- требования (функциональные и нефункциональные) и роли;
- диаграммы вариантов использования;
- BPMN бизнес-процессов: приёмка, размещение, комплектация, отгрузка;
- ER-диаграмма и описание таблиц;
- архитектура: слои, пакеты, интеграция с ERP;
- описание API;
- руководство пользователя по ролям;
- руководство по развёртыванию;
- результаты тестирования.
