# Архитектура SimpleWMS

Документ описывает устройство приложения и дополняется по мере прохождения этапов плана.

## Слои

```
Браузер (Thymeleaf)        ERP (JSON)
        │                      │
  MVC-контроллеры        ErpApiController (/api/v1)
        │                      │
        └──────► Сервисы бизнес-процессов ◄──────┘
                 (ReceivingProcessService, PlacementService, InventoryService)
                          │
               Репозитории Spring Data JPA
                          │
                      PostgreSQL
```

| Слой | Ответственность |
|---|---|
| Контроллеры | приём запроса, вызов сервиса, подготовка модели для шаблона / JSON-ответа |
| Сервисы процессов | правила склада, проверки, транзакции (`@Transactional`) |
| Справочные сервисы (`DefaultXxxService`) | CRUD справочников |
| Репозитории | доступ к таблицам, native-запросы выборок |
| `domain` | перечисления статусов и типов |

## Учёт остатков

Остаток хранится в `stocks` в разрезе **партия × ячейка**. Любое изменение остатка выполняется только
через `InventoryService` и сопровождается записью в журнал `stock_movements`:

| Операция | Откуда | Куда | Тип движения |
|---|---|---|---|
| Приёмка | — (0) | ячейка приёмки | `RECEIVING` |
| Размещение | ячейка приёмки | ячейка хранения | `PLACEMENT` |
| Перемещение | ячейка хранения | другая ячейка хранения | `MOVE` |
| Сборка | ячейка хранения | ячейка отгрузки | `PICKING` |
| Отгрузка | ячейка отгрузки | — (0) | `SHIPPING` |

Перемещение проверяет, что в исходной ячейке достаточно остатка; иначе операция отменяется целиком.
Поэтому сумма движений по партии всегда совпадает с её остатками.

## Процесс приёмки

```
ERP ──POST /api/v1/receivings──► Накладная «В ожидании» ──► «Отменена»
                                    │                          ▲
                                    │                          │ (пока нет строк в маршруте)
                                    │ «Начать приёмку» (кладовщик, дата)
                                    ▼
                               «В процессе» ──► приёмка строк:
                                    │            факт, срок годности, целевая ячейка
                                    │            → партия (batches)
                                    │            → остаток в ячейке приёмки + движение RECEIVING
                                    │ «Завершить приёмку»
                                    ▼
                               «Завершена»
```

Правила:
- строки принимаются только в статусе «В процессе», каждая строка — один раз;
- ошибочно принятую строку можно отменить и принять заново, пока она не в маршруте размещения
  (остаток списывается движением `ADJUSTMENT`, партия помечается удалённой);
- завершить приёмку можно только когда обработаны все строки;
- накладную можно отменить в статусах «В ожидании» и «В процессе», если ни одна строка не в маршруте размещения;
- повторная загрузка накладной с тем же номером ERP отклоняется, пока прежняя не отменена;
- для товаров с признаком «срок годности» дата обязательна;
- при нулевом факте строка закрывается без создания партии;
- накладная из ERP создаётся целиком в одной транзакции; неизвестный поставщик или неверное количество отклоняют её полностью, неизвестные товары пропускаются с предупреждением в ответе.

## Размещение

**Единицы:** объём товара (`product.volume`) и вместимость ячейки (`location.capacity`) — литры (дм³).

**Формирование маршрутов** (`PlacementService.generateRoutes`, кнопка «Сформировать маршруты»):
берутся остатки в ячейке приёмки, по которым ещё нет маршрута. Ячейка для каждой партии:
- выбранная при приёмке строки (если выбрана и это действующая ячейка хранения);
- иначе подбирается автоматически (`PlacementCellPicker`), внутри каждого шага — сначала зона для ABC-класса
  товара (`wms.placement.abc-zones`), затем ближайшие ячейки (ряд, x, y, z):
  1. ячейка, где уже лежит этот товар и хватает места;
  2. пустая ячейка;
  3. любая ячейка, где хватает места.

Занятость = остатки + ещё не размещённые строки открытых маршрутов. Если места нет — строка остаётся
в зоне приёмки, в уведомлении сообщается «не хватило места». Маршруты создаются по одному на зону хранения;
строка прихода отмечается (`placement_route = true`).

**Исполнение:**

```
«Создан» ──взять в работу──► «В работе» ──подтверждение всех строк──► «Завершён»
    └──────────── отмена (пока ни одна строка не размещена) ────────────► «Отменён»
```

Подтверждение строки — движение `PLACEMENT` из ячейки приёмки в плановую или фактически выбранную ячейку
хранения (системные ячейки запрещены). Отмена маршрута снимает отметку со строк прихода — товар
попадёт в следующий маршрут. Лист размещения для печати — `/product_placement/print/{id}`.

**Занятость ячейки** (`location.available`): 0 — в ячейке есть товар, 1 — свободна; обновляется
`InventoryService` при каждом движении (для системных ячеек не ведётся).

## Обработка ошибок

| Ситуация | Интерфейс | REST API |
|---|---|---|
| `WmsException` (нарушено правило) | уведомление на странице (cookie `alertMessage`) или страница ошибки с текстом | 400, `{"success":0,"message":"..."}` |
| `NotFoundException` | страница ошибки с текстом, 404 | 404, JSON |
| Некорректный JSON | — | 400, JSON |
| Прочие ошибки | стандартная страница ошибки, запись в журнал | 500, JSON |

## Перемещение

Страница «Перемещение товара» (`TransferService`):
- содержимое выбранной ячейки (товар, партия, срок годности, количество);
- «где лежит товар» — поиск по коду, части названия или штрихкоду;
- перемещение партии целиком или частично между ячейками хранения — движение `MOVE`;
- журнал последних 30 перемещений (дата, товар, партия, откуда, куда, количество, сотрудник).

Правила: только между действующими ячейками хранения (системные ячейки приёмки и отгрузки запрещены —
туда и оттуда товар попадает маршрутами размещения и сборки), не больше остатка партии в ячейке.
Нехватка места в ячейке-получателе — предупреждение, а не запрет: фиксируется фактическое положение товара.

## Заказы клиентов и резервирование

Таблицы: `customer_order` (заголовок), `customer_order_line` (заказано / в резерве / собрано / отгружено),
`stock_reservation` (резерв «строка заказа × партия × ячейка»). Свободный остаток = `stocks.quantity` − резервы.

```
«Новый» ──резерв──► «Зарезервирован» ──► «В сборке» ──► «Собран» ──► «Отгружен»
   │        └──нехватка──► «Частично зарезервирован» ──дорезервирование──┘
   └────────── отмена (до передачи в сборку, резерв снимается) ──────────► «Отменён»
```

- Источник заказа — ERP (`POST /api/v1/orders`, резерв сразу) или страница «Заказы» (создание, строки, «Зарезервировать»).
- Повторный номер заказа отклоняется, пока прежний не отменён.
- Резервирование по FEFO: ближайший срок годности первым, без срока — последними, затем ранний приход;
  только ячейки хранения (не приёмка и не отгрузка). Повторное резервирование добирает недостающее.
- Перемещение (`TransferService`) разрешено только для свободной части остатка.

Формат заказа из ERP — раздел «API для ERP».

## Комплектация (сборка заказа)

Таблицы: `picking_route` (маршрут сборки, один на заказ), `picking_route_line` (строка = один резерв:
ячейка × партия × план / собрано). Статусы маршрута — `PickingRouteStatus`: «Создан», «В работе», «Завершён», «Отменён».

1. Менеджер в карточке полностью зарезервированного заказа нажимает «Передать в сборку» →
   создаётся маршрут, строки упорядочены по обходу склада (зона, ряд, x, y, z), заказ → «В сборке».
2. Кладовщик на странице «Комплектация заказа» (`/picking_route_list`) берёт маршрут в работу и по каждой строке
   вводит фактически собранное количество (0…план).
3. Подтверждение строки: собранное перемещается из ячейки в ячейку отгрузки (`wms.locations.shipping-id`,
   движение «Сборка»), резерв строки удаляется, в строке заказа растёт «собрано».
   Если собрано меньше плана — недостача: на эту разницу уменьшается «в резерве», остаток в ячейке не списывается
   (расхождение решается инвентаризацией).
4. Последняя строка → маршрут «Завершён», заказ «Собран».
5. Отмена маршрута возможна, пока не подтверждена ни одна строка: заказ возвращается в «Зарезервирован», резервы сохраняются.

Сборочный лист (`/picking_route_list/print/{id}`) — шаблон `piccking_list.html` с данными маршрута.

## Отгрузка

Таблицы: `shipment` (документ `ОТГ-<id>`, заказ, кто и когда отгрузил, `exported_at` — когда ERP подтвердила получение),
`shipment_line` (строка заказа × партия × количество).

- Отгрузить можно только заказ в статусе «Собран» и только один раз. Кнопка «Отгрузить» — на странице «Отгрузка заказа»
  (`/shipping_list`, все роли) и в карточке заказа.
- Строки берутся из завершённого маршрута сборки (фактически собранное, строки с 0 пропускаются).
  Каждая строка списывается из ячейки отгрузки движением «Отгрузка» (`InventoryService.writeOff`, «куда» = 0),
  в строках заказа заполняется «отгружено», заказ → «Отгружен». Недостача при сборке = «заказано» − «отгружено».
- Документ создаётся сразу проведённым (без черновика): товар уже собран и лежит в зоне отгрузки.
- Печать: ТОРГ-12 (`/shipping_list/torg_12/{id}`) — тот же шаблон `torg-12.html`, что и для прихода; шапка передаётся
  в модели `doc` (грузоотправитель, поставщик, грузополучатель, плательщик, основание, номер).

Выгрузка в ERP:

```
GET  /api/v1/shipments?from=2026-10-01      (по умолчанию — последние 30 дней)
POST /api/v1/shipments/{id}/confirm         ERP подтверждает получение
```

```json
{"success": true, "message": "Отгрузок: 1",
 "data": [{"id": 1, "number": "ОТГ-1", "orderERP": "ПР-1", "customerCode": "К000001",
           "shipDate": "2026-10-10 19:19:21", "confirmed": false,
           "body": [{"code": "074519", "qnt": 50}, {"code": "029952", "qnt": 18}]}]}
```

## Отчёты и главная страница

`ReportService` строит отчёты SQL-запросами только на чтение (`NamedParameterJdbcTemplate`) — фильтры и агрегаты
проще собирать так, чем через репозитории сущностей. Отчёты доступны администратору и менеджеру.

| Страница | Что показывает |
|---|---|
| `/` — сводка по складу | приходы к приёмке, партии без маршрута размещения, заказы к резервированию / в сборку / к отгрузке, маршруты сборки в работе, партии с истёкшим и истекающим сроком; кладовщик видит только складские карточки |
| `/warehouse_status` — состояние склада | по товарам (всего, в хранении, резерв, свободно, в приёмке, в зоне отгрузки); по партиям и ячейкам (срок годности, резерв); загрузка ячеек (объём, вместимость, % заполнения). Фильтры: товар, зона, ячейка, «только с истекающим сроком» |
| `/movement_journal` — журнал движений | все записи `stock_movements` с фильтрами по периоду, типу, товару, партии; по 50 записей на страницу |
| `/shipment_report` | отгрузки за период по клиентам (документы, штуки, вес) и по товарам (заказано, отгружено, недогруз) |
| `/income_report` | завершённые приходы за период (по дате начала приёмки) по поставщикам и товарам: ожидалось, принято, расхождение |
| `/report_pickers` | работа сотрудников за период: завершённые маршруты сборки (строки, штуки, недостачи) и размещения |

Период отчётов по умолчанию — с начала текущего месяца по сегодня. Подсветка сроков: красный — истёк,
жёлтый — истекает в ближайшие `wms.expiry.warning-days` дней.

## API для ERP

Контроллер `ErpApiController`, адрес `/api/v1`, описание — Swagger UI `/swagger-ui.html` (springdoc, вход
администратором или менеджером; для «Try it out» нажать «Authorize» и ввести ключ). Обмен с ERP — `ErpService`
(справочники, статусы документов), загрузка документов — `ReceivingProcessService` и `OrderService`.

| Метод | Адрес | Назначение |
|---|---|---|
| PUT | `/products`, `/suppliers`, `/customers` | справочники: создание или обновление по коду, все записи или ни одной |
| POST | `/receivings` | приходная накладная («В ожидании»); неизвестные товары пропускаются (`missingProducts`) |
| GET | `/receivings/{номер}` | статус накладной и строки «ожидалось / принято / срок годности» |
| GET | `/receivings?from=ГГГГ-ММ-ДД` | выгрузка завершённых приёмок |
| POST | `/orders` | заказ клиента, сразу резерв по FEFO (`status`, `shortage`) |
| GET | `/orders/{номер}` | статус заказа и «заказано / в резерве / собрано / отгружено» по строкам |
| POST | `/orders/{номер}/cancel` | отмена до передачи в сборку |
| GET | `/shipments?from=ГГГГ-ММ-ДД` | выгрузка отгрузок |
| POST | `/shipments/{id}/confirm` | ERP подтверждает получение отгрузки |

Формат ответа (`ApiResponse`): `{"success": true, "message": "...", "data": ...}`, при ошибке —
`{"success": false, "message": "...", "errors": [{"field": "lines[0].quantity", "message": "должно быть больше 0"}]}`.

| Код | Когда |
|---|---|
| 200 / 201 | успешно (201 — создан документ) |
| 400 | ошибки проверки (`@Valid`), некорректный JSON, неверный формат даты или числа |
| 401 | нет ключа или неверный ключ |
| 403 | нет прав; запрос из браузера с сессией без CSRF-токена |
| 404 | документ, поставщик, клиент не найдены |
| 409 | дубль номера, недопустимый статус, повтор кода в запросе |

Даты: документ — `ГГГГ-ММ-ДД ЧЧ:ММ:СС`, плановая отгрузка и параметр `from` — `ГГГГ-ММ-ДД`; количества — числа.
Сообщения проверки — на русском (`spring.web.locale=ru`).

Пример заказа:

```json
{"number": "ПР-100", "customerCode": "К000001", "date": "2026-10-10 09:00:00", "shipDate": "2026-10-11",
 "note": "необязательно", "lines": [{"code": "029952", "quantity": 20}, {"code": "074519", "quantity": 10}]}
```

Имитация ERP:
- страница «Интеграция с ERP → Имитация ERP» (`/erp_simulator`): готовые запросы из `resources/erp-samples`,
  можно править и отправлять, ответ API показывается на странице;
- `Project_Docs/api/erp.http` — запросы для IntelliJ IDEA / VS Code REST Client, `Project_Docs/api/samples/` — примеры JSON;
- `Project_Docs/api/erp-demo.ps1` — PowerShell-скрипт: справочники → накладная → заказ → проверка ошибок → выгрузка отгрузок.

## Безопасность

**Вход в интерфейс** — форма `/login`, учётные записи в таблице `users` (пароли — BCrypt).
Права определяются ролью сотрудника, к которому привязан пользователь (`users.employeeid → employee.roleid`):

| Роль (`roles.roleid`) | Доступ |
|---|---|
| Администратор (1) | всё, включая «Администрирование»: сотрудники, пользователи, роли |
| Менеджер склада (2) | складские операции, справочники, заказы, отчёты |
| Кладовщик (3) | складские операции: приёмка, размещение, перемещение, комплектация, отгрузка |

Пользователь удалённый (`users.del`) или привязанный к удалённому сотруднику — не может войти.
Пользователь с ролью, не входящей в таблицу, входит, но не имеет доступа к разделам.
Пункты меню скрываются по роли (`sec:authorize`), запрет проверяется и на сервере (403 — страница «Недостаточно прав»).

**Исполнитель операций** — сотрудник вошедшего пользователя (`CurrentUser`); он записывается в журнал движений.

**Защита от подделки запросов (CSRF)** — все POST-формы содержат токен (`th:action`), AJAX-запросы
передают его в заголовке (`<meta name="_csrf">` + `$.ajaxSetup` в `js/scripts.js`).

**REST API (`/api/**`)** — два способа доступа:

| Клиент | Аутентификация | CSRF |
|---|---|---|
| ERP / внешняя система | заголовок `X-API-Key` = `wms.api.key` (переменная `WMS_API_KEY`) | не требуется |
| Страницы интерфейса (AJAX) | сессия пользователя с ролью Администратор или Менеджер | токен в заголовке |

Неверный ключ и запрос без ключа и без сессии — 401 с JSON-сообщением. Пустой ключ в настройках отключает доступ по ключу.
Swagger UI (`/swagger-ui.html`, `/v3/api-docs`) и «Имитация ERP» — только администратор и менеджер.

**Пароли, сохранённые открытым текстом** до этапа 2, при старте приложения автоматически переводятся в BCrypt (`PasswordMigration`).

## Настройки склада

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `wms.locations.receiving-id` | 1 | ячейка зоны приёмки |
| `wms.locations.shipping-id` | 2 | ячейка зоны отгрузки |
| `wms.company.name` | Склад SimpleWMS | наименование склада в ТОРГ-12 и сборочном листе |
| `wms.placement.abc-zones.<A/B/C/D>` | нет (dev: A,B→SC1; C,D→SC2) | предпочтительная зона хранения для ABC-класса |
| `wms.api.key` | пусто (dev: `dev-api-key`) | ключ доступа ERP к REST API |
| `wms.expiry.warning-days` | 30 | за сколько дней до окончания срока партия подсвечивается как «истекает» |
